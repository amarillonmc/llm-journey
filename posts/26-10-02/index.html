USER：

就在这台Windows Server独立服务器上，这几天RDP剪贴板功能突然失效了。外见表象即无法通过宿主机复制→本机粘贴的手段移动文件，反过来也同样不成立。

我在进行连接时已经选中了共享剪贴板的选项。且已经尝试重新连接。

我本机同时连接着多个RDP，甚至有个RDP中还在连接另一个RDP，都共享了剪贴板，我甚至可以在宿主机中复制，在RDP中的RDP里面将内容正常粘贴。

这台机器的rdpclip.exe的确正在运行。

何故？

GPT：

从你描述的情况看，我会首先怀疑“这台服务器当前会话的剪贴板同步卡住”，其次才是“文件传输被单独限制”。 目前没有理由把它简单归结为“RDP 开得太多”，也不需要先重启整台服务器。

你已经检查的几项，并不能完全排除这两种问题：

rdpclip.exe 还在，不代表它仍在正常同步。 微软问答中有与你很接近的实际报告：进程仍然存在，但剪贴板不再同步，结束并重新启动它后恢复。因此，“确认它正在运行”和“重新初始化它”是两回事。Microsoft Learn

断开后重连，也不等于重新创建用户会话。 Windows 会保留断开会话中的程序；重新连接可能只是回到原来的桌面和进程状态。因此，你已经尝试重连，却没有恢复，并不奇怪。Microsoft Learn

另外，你目前明确描述的是文件无法复制，尚不能确定普通文字是否也受影响——这是下面排查中最重要的分界。

一、先分清：只有文件不行，还是文字也不行？

在本机和这台服务器上各打开一个记事本，尝试双向复制一小段新输入的普通文字。然后，使用资源管理器，双向复制一个桌面上的小 .txt 文件。

测试文件尽量只有几 KB，复制到另一端的桌面即可，暂时不要用大型备份、压缩包内部的文件或受保护的系统目录。

测试结果优先排查方向跨 RDP 的文字、文件都不行，但两端各自内部复制正常当前会话的剪贴板同步状态、该连接的客户端状态、剪贴板禁用策略文字正常，只有文件不行文件重定向策略、文件传输状态小文件正常，只有大文件不行文件大小限制，而不一定是剪贴板整体故障服务器内部的记事本之间也不能复制文字排查范围应扩大到该用户会话本身，而不只是 RDP

之所以必须区分，是因为微软明确说明：服务器策略禁止“驱动器重定向”时，也会禁止通过剪贴板复制文件，但普通文字和图片不受这个策略影响。 所以，“勾选了共享剪贴板”并不必然意味着文件复制也被允许。Microsoft Learn

二、第一项修复：只重启当前会话的 rdpclip.exe

这一步最值得先试。在出问题的服务器桌面内，以当前登录用户打开普通 PowerShell，执行：

# 获取当前 PowerShell 所在的用户会话
$sessionId = (Get-Process -Id $PID).SessionId

# 只结束当前会话的 RDP 剪贴板进程，不动其他会话
Get-Process -Name rdpclip -ErrorAction SilentlyContinue |
    Where-Object { $_.SessionId -eq $sessionId } |
    Stop-Process -Force -ErrorAction Stop

Start-Sleep -Milliseconds 500

# 在当前会话中重新启动
Start-Process "$env:WINDIR\System32\rdpclip.exe"

执行完毕后，重新复制一段文字，再重新复制那个小文件，测试双向传输。

这段命令只操作当前会话中的 rdpclip.exe，不重启 IIS、MySQL 或远程桌面服务，也不结束其他会话的剪贴板进程。结束并重新启动 rdpclip.exe 本身也是微软支持回复给出的排查方法。Microsoft Learn

若连文字也无法粘贴进去，可以直接在服务器里打开任务管理器，结束属于你当前会话的 rdpclip.exe，然后通过“文件 → 运行新任务”输入：

rdpclip.exe

不要只再启动一次而不结束旧进程；这里要做的是重建它的运行状态。

如果这一步立即恢复，便支持“会话内运行状态异常”这个判断，而不是简单的配置禁用；但还不能仅凭恢复，就认定最初究竟是哪一个程序或操作触发了异常。

三、若文字正常、文件仍然失败，检查这两个策略

在服务器上执行以下只读查询：

reg query "HKLM\SOFTWARE\Policies\Microsoft\Windows NT\Terminal Services" /v fDisableClip

reg query "HKLM\SOFTWARE\Policies\Microsoft\Windows NT\Terminal Services" /v fDisableCdm

对应含义如下：

项目显示为 0x1 时的含义fDisableClip禁止剪贴板重定向fDisableCdm禁止驱动器重定向，同时会禁止剪贴板文件复制

这两个值对应的策略名称和注册表位置，分别列在微软的剪贴板及驱动器重定向策略文档中。Microsoft Learn

若显示“找不到指定的注册表项或值”，不代表故障，只是这个位置没有显式配置该项；也不能据此断言所有层面的重定向设置都正常。

图形界面可以运行 gpedit.msc，进入：

计算机配置 → 管理模板 → Windows 组件 → 远程桌面服务 → 远程桌面会话主机 → 设备和资源重定向

重点查看：

  • 不允许剪贴板重定向
  • 不允许驱动器重定向

若其中某项被启用，而且不是你有意设置的限制，再从对应的策略来源修改。允许这些功能时，这两个“不允许……”策略应为“已禁用”或没有其他上级限制的“未配置”，注意这里的双重否定。Microsoft Learn

还有一项容易被旧教程漏掉：支持较新剪贴板控制功能的系统，还可能配置了按方向、按数据类型限制的策略，即 CSClipLevel、SCClipLevel，并且可以来自计算机或当前用户配置。它们能造成“文字允许、文件不允许”；不要照着其他禁用开关的思路把它们一律改成 0，因为这里的 0 表示禁止该方向的剪贴板传输。 Microsoft Learn

目前先查询即可，不建议直接批量改注册表，更不要删除整个 Terminal Services 策略键。

四、多连接和嵌套 RDP：做隔离测试，但不要直接认定它们是原因

你已有“本机 → RDP → 内层 RDP”可以正常复制的实测，因此，“存在多连接或嵌套”本身不是足够的故障解释。

但其他连接正常，也只能说明它们正常，不能证明这台服务器对应的连接状态没有问题。若第二步没有修好，可以做一次对照实验：

临时断开其他 RDP，包括内层连接，不是注销那些服务器的用户；只保留本机直连这台故障服务器。随后重新执行一次当前会话的 rdpclip 重启，再测试文字和小文件。断开会话与注销不同，前者会保留会话中的运行程序。Microsoft Learn

如果单连接时恢复，再逐个恢复其他连接，观察故障是否随某一个连接重新出现。如果单连接仍失败，就没有必要继续把重点放在“开了太多 RDP”上。

这里不建议一刀切执行 taskkill /IM mstsc.exe /F，也不建议重启服务器的 TermService。 对你这种同时维护多个远程桌面、服务器上又跑着实际业务的情况，先把操作范围限制在目标连接和当前会话更合适。

五、你最近在做备份，还要排除“大文件看起来像剪贴板失效”

假如失败对象主要是刚生成的大型 .7z、.sql 文件，而几 KB 的测试文件正常，就要注意另一个独立问题：

微软文档列明，传统 RDP 剪贴板方式复制超过 2 GB 的文件可能直接失败，而且不显示错误。 这不等于整个共享剪贴板坏了。Microsoft Learn

这种情况下，可以在连接选项中进入：

本地资源 → 详细信息 → 驱动器

只勾选需要传文件的本地磁盘，重新连接后，在服务器资源管理器中访问：

\\tsclient\

例如重定向了本机 C 盘，就可以通过：

\\tsclient\C\

访问本地文件，再在服务器内通过该路径复制。微软也将驱动器重定向列为大文件传输的替代方法。不过，它仍然受前面“禁止驱动器重定向”策略的约束。 Microsoft Learn

就你目前的描述，最先该做的不是重装、重启或停掉 Defender，而是第二节：结束并重建当前会话的 rdpclip.exe。 “它确实正在运行”恰好还没有排除这一类故障。

接下来最有判别力的反馈是：重启它后是否恢复，以及普通文字和几 KB 小文件分别能否双向复制；若只有文件失败，再看两个策略查询的输出。

这下基本定位到故障层面了：更符合“当前 RDP 会话中文件剪贴板重定向的临时状态异常”，而不是配置没有打开。 关键证据是你没有更改任何策略，只重启了 rdpclip.exe，文件传输便恢复了。

两个注册表查询报错，不需要处理

这里的：

ERROR: The system was unable to find the specified registry key or value.

意思只是：在查询的注册表位置，没有找到指定的键或值。 它不是在报告“RDP 组件损坏”或者“系统缺少必要配置”。reg query 本身就是查询命令，指定目标不存在时会查询失败。Microsoft Learn

所以，对你这次查询，准确理解是：那个计算机级策略路径下没有显式设置这两个值，而不是“需要把它们补上”。Windows 本身默认不阻止剪贴板及驱动器重定向，相应的“不允许……”策略也支持保持“未配置”。Microsoft Learn

严格说，缺少这两个值不能单独证明所有其他配置来源都没有限制；但结合你现在已经恢复双向文件复制的实测，目前没有必要继续修改注册表或组策略，保持原样即可。

“文字能复制、文件不能复制”，也可能是运行状态故障

这个补充也很重要，我上一条的排查表需要加一个限定：

文字正常、文件失败时，应当检查文件相关限制，但不能仅凭这个症状就认定是策略问题。

微软确实明确区分了这两类行为，例如禁止驱动器重定向可以阻止剪贴板文件传输，却不影响文字或图片。也就是说，“文字正常”并不能证明文件相关功能同样正常。Microsoft Learn

而你的实际结果进一步说明：至少这一次，文件复制故障可以通过重新初始化 rdpclip.exe 恢复，即使它此前还活着、文字复制也正常。 因而用“整个进程完全卡死”来描述也不够准确，更合适的是“文件重定向相关状态异常”。

现在可以停在这里，不用继续折腾服务器。 留着第二步那段“只重启当前会话 rdpclip.exe”的脚本作为手动恢复手段即可；若之后频繁复发，再记录复发前的具体操作来追查触发条件，而不是先动全局配置。
